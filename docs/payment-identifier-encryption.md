# Payment-identifier encryption

Migration `20261013100000_encrypt_payment_identifiers.sql` encrypts
`users.mobile_money_number` and `users.bank_account_number` at rest with
AES-256 OpenPGP encryption. Each encryption operation is randomized; the same
number produces different ciphertext each time. There is intentionally no
lookup hash or identifier index because Tshelo has no approved exact-match use
case for these values.

The migration creates a 256-bit key inside Supabase Vault named
`payment_identifiers_encryption_v1`. The key is generated by PostgreSQL and is
not committed, printed, stored in an environment variable, or supplied to the
mobile/web clients. Vault keeps the secret encrypted at rest.

## Deployment and verification

The original migration is already applied to the linked production project.
It backfilled encrypted columns and cleared both plaintext columns in the same
transaction. New environments should apply both migrations through the standard
migration process, first in staging. Verify:

1. Existing identifiers decrypt accurately through
   `get_payment_identifiers_for_service` under `service_role`.
2. `authenticated` and `anon` cannot execute any encryption/decryption helper or
   the service retrieval routine, cannot read Vault's decrypted secrets, and
   cannot write ciphertext/key-version columns. Legacy number columns stay NULL.
3. An authenticated call to `update_own_payment_details` stores ciphertext,
   clears the matching verified flag, and emits the security notification.
4. The retired plaintext columns contain no non-null values.

Do not restore plaintext columns for troubleshooting. Use the service-only
routine in a tightly authorized backend workflow and avoid logging its result.
Provider verification and payout integrations should call that routine only at
the final provider request boundary.

## Rotation and recovery

This initial migration records key version `1` on every user. The current helpers
resolve v1 explicitly; changing only the row version or Vault name is not a
supported rotation. A real rotation needs a reviewed migration that introduces
v2-aware reads/writes, locks or safely coordinates writers, decrypts with v1,
re-encrypts with v2, updates row versions, and verifies every affected row before
switching reads. Keep v1 until all relevant recovery points have expired or have
been verified recoverable. A failed atomic migration must roll back; never
restore plaintext as a workaround.

The verification test rehearses the decrypt/re-encrypt operation with a fresh
in-memory key. It does not rotate the live key or prove a complete Vault/backup
restore. Before an actual rotation, test that migration and concurrency/recovery
procedure in an isolated restored project.

Recovery must preserve both the encrypted rows and the corresponding Vault
secret/root-key access. Restrict recovery operations to designated database
administrators; do not export the key into application configuration or logs.
Restore to an isolated environment first, deny client access, apply security
migrations as appropriate, then run the encryption test below. Compare controlled
samples inside the database and release only pass/fail evidence. If the matching
key is unavailable, stop payout/verification use and escalate to the recovery
owner; ciphertext cannot be recovered by recreating a secret with the same name.

## Exposure review and release limits

The reviewed current API profile response uses an explicit field list that
omits identifiers and ciphertext. Profile writes route identifiers through
`update_own_payment_details`. API database-error logging emits request ID/error
code rather than request bodies or database error details. The fund-report SQL
uses explicit fields and does not read payment identifiers. Live user triggers
do not copy complete profile rows into audit history. A live aggregate scan
found no payment-identifier field names in audit old/new JSON, no identifiers in
payment-change notifications, and an empty SMS log. Only the payment update and
service retrieval functions reference these number fields in public function
bodies. These scoped checks do not certify arbitrary historical free text,
downloaded exports, provider logs or external telemetry.

The held web/mobile release remains necessary: the older web deployment predates
the controlled payment-update integration. A passing database RPC test is not a
passing deployed website/app payment-flow test. Legacy plaintext columns remain
present but constrained to NULL for compatibility; dropping them is deferred
until the release and recovery checks are complete.

Encryption does not rewrite backups or old downloaded exports. Treat recovery
points from before the backfill as potentially containing plaintext, restrict
operator access, and apply the approved provider retention policy. Do not purge
backups as part of this migration. Historical provider/telemetry inspection and
an isolated backup restore remain outstanding; no recovery claim is made here.

Live backup metadata lists eight completed physical backups dated 8–15 October
2026; PITR is disabled. Older recovery points therefore still exist and must be
handled as potentially containing plaintext. Backup contents were not downloaded
or restored, and no backup was deleted or modified.
