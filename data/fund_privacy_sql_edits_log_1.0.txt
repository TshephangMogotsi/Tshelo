TSHELO FUND PRIVACY + JOIN APPROVAL — SQL TO APPLY
====================================================

Purpose
-------
Supports a public/private toggle on fund creation. Public funds: joining by
invite code is instant, same as today. Private funds: joining by invite code
creates a fund_members row with status='pending'; the fund owner/admin must
approve or reject it before the requester becomes a full member.

This file was written by Claude Code but NOT applied — the CLI session had
no SUPABASE_ACCESS_TOKEN, so it could not run against the linked project
(albihofmlafjzbusancu) non-interactively. Run this manually via the
Supabase Dashboard SQL Editor, or `supabase login` locally then
`supabase db query --linked -f this_file`.

No new enum values are introduced. The existing member_status values
'pending' (already the column default) and 'declined' (already used
elsewhere in the app to mean "this membership doesn't count") are reused
for "awaiting approval" and "rejected by admin" respectively.


1. Privacy toggle on funds
----------------------------

ALTER TABLE public.funds
  ADD COLUMN is_private boolean NOT NULL DEFAULT false;


2. Let fund owner/admin approve or reject a pending join request
--------------------------------------------------------------------

No UPDATE policy exists on fund_members today (verified against the
2026-06-05 RLS snapshot) — without this, an owner/admin's client-side
.update() on a member's status would be silently blocked by RLS.

CREATE POLICY "fund_members_update_manager"
ON public.fund_members
FOR UPDATE
TO authenticated
USING (is_fund_owner(fund_id) OR is_fund_admin(fund_id))
WITH CHECK (is_fund_owner(fund_id) OR is_fund_admin(fund_id));


3. Let a pending requester see the fund they're waiting on
------------------------------------------------------------

funds_select_member currently only allows the owner or a status='joined'
member to read a fund row. Widened to also allow status='pending', so a
requester can see the fund's title/goal on their "Request Sent" screen
instead of a bare UUID. This is the one modification to an EXISTING
policy in this migration — reviewed carefully since altering the wrong
clause here could over-expose fund data:

DROP POLICY IF EXISTS "funds_select_member" ON public.funds;

CREATE POLICY "funds_select_member"
ON public.funds
FOR SELECT
TO public
USING (
  (owner_id = auth.uid())
  OR EXISTS (
    SELECT 1 FROM fund_members
    WHERE fund_members.fund_id = funds.id
      AND fund_members.user_id = auth.uid()
      AND fund_members.status IN ('joined', 'pending')
  )
);


4. Companion RPC so a prospective joiner can check privacy before joining
----------------------------------------------------------------------------

find_fund_by_code (used by JoinFundScreen today) already does a
security-definer-style lookup by code across all funds regardless of
membership, presumably to bypass funds_select_member for the "search by
code" step. Its current body wasn't readable in this session (same auth
wall), so rather than blindly CREATE OR REPLACE it and risk breaking its
existing behaviour, this adds a small standalone companion function
instead:

CREATE OR REPLACE FUNCTION public.get_fund_privacy(p_fund_id uuid)
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT is_private FROM public.funds WHERE id = p_fund_id;
$$;

GRANT EXECUTE ON FUNCTION public.get_fund_privacy(uuid) TO authenticated;


Result once applied
--------------------
- CreateFundScreen can write is_private on insert.
- JoinFundScreen can call get_fund_privacy(fund.id) after find_fund_by_code
  resolves, and insert status='pending' instead of 'joined' when true.
- FundDetailScreen (owner/admin) can list fund_members rows with
  status='pending' (already selectable — no SELECT policy change needed,
  any joined member can already see all member rows for their fund) and
  update a row's status to 'joined' (approve) or 'declined' (reject).
