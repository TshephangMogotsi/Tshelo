TSHELO EVENT CREATION DATABASE INSTRUCTIONS
===========================================

Purpose
-------
These changes align the Create Event screen with the database and make event
creation flexible, reliable, and safe.


1. REPLACE events.event_type ENUM WITH CHARACTER VARYING
---------------------------------------------------------

Why:
- The app allows users to select "Other" and enter a custom event type.
- A PostgreSQL enum only accepts predefined values.
- Adding a new enum value requires a database migration.
- A text value allows standard types such as "wedding" and custom types such
  as "retirement-party".

Recommended SQL:

ALTER TABLE public.events
ALTER COLUMN event_type TYPE character varying
USING event_type::text;

Validation:
- Standard event types should be validated against public.event_type_config.
- Trim custom event types and enforce a sensible maximum length in the app.


2. ADD event_emoji TO public.events
-----------------------------------

Why:
- The Create Event screen lets the user choose an emoji.
- The current events table has nowhere to store the selected emoji.
- Without this field, the emoji is lost after leaving the creation screen.

Recommended SQL:

ALTER TABLE public.events
ADD COLUMN event_emoji character varying;

Notes:
- Use character varying rather than character(1), because some emojis contain
  multiple Unicode characters.
- The app should use the configured default emoji for standard event types and
  the selected emoji for custom event types.


3. GENERATE event_code AND share_code IN THE DATABASE
------------------------------------------------------

Why:
- public.events requires event_code, but the Create Event screen does not
  currently generate one.
- share_code is needed for public RSVP links.
- Database generation ensures every event creation path receives valid codes.
- Unique constraints protect against duplicates, but generation logic should
  still use random, difficult-to-guess values.

Recommended approach:
- Create database functions that generate random event and share codes.
- Set those functions as defaults for events.event_code and events.share_code.
- Keep the existing UNIQUE constraints.
- Use enough random characters to make collisions and guessing unlikely.
- Do not use sequential or easily predictable RSVP share codes.

Safe SQL:

CREATE OR REPLACE FUNCTION public.generate_event_code()
RETURNS character varying
LANGUAGE plpgsql
AS $$
DECLARE
  candidate character varying;
BEGIN
  LOOP
    candidate := 'EVT-' || upper(substr(replace(gen_random_uuid()::text, '-', ''), 1, 8));

    EXIT WHEN NOT EXISTS (
      SELECT 1
      FROM public.events
      WHERE event_code = candidate
    );
  END LOOP;

  RETURN candidate;
END;
$$;

CREATE OR REPLACE FUNCTION public.generate_share_code()
RETURNS character varying
LANGUAGE plpgsql
AS $$
DECLARE
  candidate character varying;
BEGIN
  LOOP
    candidate := upper(substr(replace(gen_random_uuid()::text, '-', ''), 1, 10));

    EXIT WHEN NOT EXISTS (
      SELECT 1
      FROM public.events
      WHERE share_code = candidate
    );
  END LOOP;

  RETURN candidate;
END;
$$;

ALTER TABLE public.events
ALTER COLUMN event_code SET DEFAULT public.generate_event_code();

ALTER TABLE public.events
ALTER COLUMN share_code SET DEFAULT public.generate_share_code();

Important:
- The generate_event_code() and generate_share_code() functions must be created
  before applying these defaults.
- If generate_event_code() already exists, use the same return type as the
  existing function. The events columns are character varying, so the safest
  return type is character varying.
- Code-generation functions should handle the unlikely event of a collision.
- These examples use gen_random_uuid(), which is available in Supabase/Postgres
  through pgcrypto. If your project does not already have it, run:
  CREATE EXTENSION IF NOT EXISTS pgcrypto;

If event creation fails with "value too long for type character varying(10)":
- The live database still has a 10-character limit on event_code or share_code.
- The generated event code format "EVT-" plus 8 random characters is 12
  characters.
- Widen both columns so they match the schema reference:

ALTER TABLE public.events
ALTER COLUMN event_code TYPE character varying;

ALTER TABLE public.events
ALTER COLUMN share_code TYPE character varying;


4. LOAD STANDARD EVENT TYPES FROM event_type_config
----------------------------------------------------

Why:
- Event types are currently hardcoded in CreateFundScreen.tsx.
- public.event_type_config already stores event type, display name, icon,
  ordering, active status, and other configuration.
- Loading this table prevents the app and database from disagreeing.
- Administrators can add, rename, reorder, or disable event types without
  requiring a new mobile app release.

Recommended app query:

SELECT event_type, display_name, icon
FROM public.event_type_config
WHERE is_active = true
ORDER BY sort_order;

Recommended behavior:
- Display active configured types in the Create Event screen.
- Keep an "Other" option available for custom event types.
- Provide a local fallback list if the query fails or the device is offline.
- Store the selected event_type value in public.events.event_type.
- Store the selected or configured emoji in public.events.event_emoji.


5. INSERT ONLY GENUINELY SELECTED ORGANISERS
---------------------------------------------

Why:
- The Create Event screen currently displays two hardcoded example organisers.
- Saving them would create false invitations and inaccurate event data.
- It could also grant event access to people the creator did not select.

Recommended app changes:
- Remove the hardcoded Mpho Kgosi and Kago Modise organiser cards.
- Insert only contacts stored in pickedOrganisers.
- Use the newly created event ID for each event_organisers row.
- Set invited_by to the authenticated creator's user ID.
- Store contact names in invited_name and phone numbers in invited_phone.

Example organiser insert:

{
  event_id: createdEvent.id,
  invited_name: organiser.name,
  invited_phone: organiser.phone,
  invited_by: authenticatedUser.id,
  status: "pending"
}

Creator handling:
- events.creator_id already records the event owner.
- Add the creator to event_organisers only if other application features require
  every event manager to have an event_organisers row.


RECOMMENDED EVENT CREATION ORDER
--------------------------------

1. Confirm that the user is authenticated and has a public.users record.
2. Load active standard event types from public.event_type_config.
3. Validate the event name, type, date, time, and venue.
4. Insert the event into public.events.
5. Use the returned event ID to insert selected organisers.
6. Show success only after the database inserts succeed.
7. Use the returned share_code to build the RSVP sharing link.
8. Show a clear error and allow retrying if any required insert fails.


RECOMMENDED EVENT INSERT PAYLOAD
--------------------------------

{
  creator_id: authenticatedUser.id,
  name: eventName.trim(),
  event_type: isOtherEvent ? customEventType.trim() : selectedEventType,
  event_emoji: selectedEventEmoji,
  event_date: formattedEventDate,
  event_time: formattedEventTime,
  venue_name: eventVenue.trim()
}

event_code, share_code, currency_code, status, id, created_at, and updated_at
should be supplied by database defaults.


VERIFICATION CHECKLIST
----------------------

- A standard event type can be created.
- A custom event type can be created.
- The selected emoji remains visible after reopening the event.
- event_code and share_code are generated automatically and remain unique.
- The RSVP link uses the returned share_code.
- Only organisers selected by the user are inserted.
- Creating an event without organisers still succeeds.
- Failed event inserts do not show the success screen.
- Failed organiser inserts are handled and reported appropriately.
- Row Level Security policies allow authenticated creators to insert events and
  organisers while preventing unauthorized access.


RLS ERROR: infinite recursion detected in policy for relation "events"
----------------------------------------------------------------------

Cause:
- This usually happens when a public.events policy queries public.event_organisers
  and a public.event_organisers policy queries public.events.
- PostgreSQL tries to evaluate one policy, which triggers the other policy, which
  triggers the first policy again.

The recursive policies found in the exported policy CSV were:
- public.events.events_organiser_all queries public.event_organisers.
- public.events.events_guest_select queries public.event_guests.
- public.event_organisers.event_organisers_manage queries public.events.
- public.event_guests.event_guests_organiser queries public.events and
  public.event_organisers.

Fix:
- Do not make policies on these tables query each other directly.
- Put relationship checks into SECURITY DEFINER helper functions.
- Policies can call those functions without re-entering the other table's RLS
  policies.

Replacement SQL:

DO $$
DECLARE
  policy_record record;
BEGIN
  FOR policy_record IN
    SELECT schemaname, tablename, policyname
    FROM pg_policies
    WHERE schemaname = 'public'
      AND tablename IN ('events', 'event_organisers')
  LOOP
    EXECUTE format(
      'DROP POLICY IF EXISTS %I ON %I.%I',
      policy_record.policyname,
      policy_record.schemaname,
      policy_record.tablename
    );
  END LOOP;
END;
$$;

CREATE OR REPLACE FUNCTION public.is_event_creator(target_event_id uuid)
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM public.events
    WHERE id = target_event_id
      AND creator_id = auth.uid()
  );
$$;

CREATE OR REPLACE FUNCTION public.is_event_organiser(target_event_id uuid)
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM public.event_organisers
    WHERE event_id = target_event_id
      AND user_id = auth.uid()
      AND status = 'active'
  );
$$;

CREATE OR REPLACE FUNCTION public.is_event_guest(target_event_id uuid)
RETURNS boolean
LANGUAGE sql
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM public.event_guests
    WHERE event_id = target_event_id
      AND user_id = auth.uid()
  );
$$;

ALTER TABLE public.events ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.event_organisers ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.event_guests ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.event_budgets ENABLE ROW LEVEL SECURITY;

CREATE POLICY "events_select_related"
ON public.events
FOR SELECT
TO authenticated
USING (
  creator_id = auth.uid()
  OR public.is_event_organiser(id)
  OR public.is_event_guest(id)
);

CREATE POLICY "events_insert_own"
ON public.events
FOR INSERT
TO authenticated
WITH CHECK (creator_id = auth.uid());

CREATE POLICY "events_update_own"
ON public.events
FOR UPDATE
TO authenticated
USING (
  creator_id = auth.uid()
  OR public.is_event_organiser(id)
)
WITH CHECK (
  creator_id = auth.uid()
  OR public.is_event_organiser(id)
);

CREATE POLICY "event_organisers_select_related"
ON public.event_organisers
FOR SELECT
TO authenticated
USING (
  invited_by = auth.uid()
  OR user_id = auth.uid()
  OR public.is_event_creator(event_id)
  OR public.is_event_organiser(event_id)
);

CREATE POLICY "event_organisers_insert_invited_by_self"
ON public.event_organisers
FOR INSERT
TO authenticated
WITH CHECK (
  invited_by = auth.uid()
  AND public.is_event_creator(event_id)
);

CREATE POLICY "event_organisers_update_related"
ON public.event_organisers
FOR UPDATE
TO authenticated
USING (
  user_id = auth.uid()
  OR public.is_event_creator(event_id)
)
WITH CHECK (
  user_id = auth.uid()
  OR public.is_event_creator(event_id)
);

CREATE POLICY "event_guests_select_related"
ON public.event_guests
FOR SELECT
TO authenticated
USING (
  user_id = auth.uid()
  OR public.is_event_creator(event_id)
  OR public.is_event_organiser(event_id)
);

CREATE POLICY "event_guests_insert_manager"
ON public.event_guests
FOR INSERT
TO authenticated
WITH CHECK (
  invited_by = auth.uid()
  AND (
    public.is_event_creator(event_id)
    OR public.is_event_organiser(event_id)
  )
);

CREATE POLICY "event_guests_update_related"
ON public.event_guests
FOR UPDATE
TO authenticated
USING (
  user_id = auth.uid()
  OR public.is_event_creator(event_id)
  OR public.is_event_organiser(event_id)
)
WITH CHECK (
  user_id = auth.uid()
  OR public.is_event_creator(event_id)
  OR public.is_event_organiser(event_id)
);

CREATE POLICY "event_budgets_manage_related"
ON public.event_budgets
FOR ALL
TO authenticated
USING (
  public.is_event_creator(event_id)
  OR public.is_event_organiser(event_id)
)
WITH CHECK (
  public.is_event_creator(event_id)
  OR public.is_event_organiser(event_id)
);

Notes:
- This avoids direct recursive subqueries in policies.
- The helper functions should be created by the database owner/admin.
- Do not enable FORCE ROW LEVEL SECURITY on these tables unless you understand
  how it changes SECURITY DEFINER behavior.
